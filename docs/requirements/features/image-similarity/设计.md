# 以图搜图 / 相似图检索 · 设计

> 状态：L2 方案（2026-10-23）；P1 库内 CLIP + dHash 已实现，其余待做  
> 上游：`需求.md`  
> 本方案先解决“如何定义相似”和“用哪些信号”，其余模式按阶段实现。

## 1. 结论先行

不要做单一的“以图搜图”分数。推荐四层：

```text
查询图
  ├─ pHash / dHash → 近似重复
  ├─ CLIP image vector → 语义相似
  ├─ DINOv2 vector → 视觉相似（同拍摄/构图）
  └─ Face embedding → 同一个人
```

默认「综合相似」用 **RRF 融合** CLIP + DINOv2，近似重复单独置顶；「同一个人」单独模式，默认不启用。VLM 文案用于文本索引，不作为以图搜图的主信号。

## 2. 本机基线（236 张测试图）

### 2.1 CLIP 图像向量

已有 Chinese-CLIP ViT-B/16 512 维向量。对图 49 做 image-to-image：

```text
49 (自身) 1.000
50        0.940  同一次拍摄/相邻图
45        0.908
48        0.887
46        0.882
47        0.868
```

图 155 的 top 结果同样是 151–161 这一组连拍。说明 CLIP 已经能处理：
- 同一次拍摄
- 同一套服装/场景
- 明显相同的构图

它不解决：
- 换装后的同一个人
- 精确近似重复
- 局部物件一致性

### 2.2 DINOv2-small（量化 ONNX，24 MB）

本机抽取 236 张，单进程约 **41.6 秒**（约 176 ms/张，未做批处理优化），384 维。

```text
DINO 49: 50 0.917, 46 0.779, 47 0.757, 45 0.736
DINO 155: 156 0.961, 160 0.942, 161 0.924, 153 0.917
DINO 18: 17 0.918, 19 0.866
```

结论：
- 与 CLIP 高度重叠，但对同一次拍摄/构图更稳定；
- 无文本能力，只适合作为第二视觉信号；
- 24 MB 量化模型值得做 A/B，不应直接替换 CLIP。

### 2.3 dHash

```text
49 → 50: Hamming 7
155 → 156: Hamming 0
18 → 无近邻（最近 22）
```

结论：
- 对完全同图/缩放/压缩很便宜；
- 对连拍、裁剪、换背景不够；
- 适合做“近似重复”专用通道，不应拿来做语义相似。

## 3. 模型与信号选择

| 信号 | 模型/算法 | 维度/大小 | 作用 | 结论 |
|---|---|---|---|---|
| 语义 | Chinese-CLIP ViT-B/16 | 512 / 182 MiB | 图文共享空间，同主题/服装/场景 | 已有，保留 |
| 视觉 | DINOv2-small 量化 ONNX | 384 / 24 MB | 同拍摄、姿态、构图、局部视觉 | 先 A/B，再决定是否默认 |
| 近似重复 | dHash/pHash | 64 bit / 无模型 | 同图缩放、压缩、轻裁剪 | 首版必做 |
| 复制检测 | SSCD | 512 / 需导出 | 更强 copy detection | 后续，不阻塞首版 |
| 人物 | SCRFD + ArcFace | 512/张脸 | 同一个人跨服装/场景 | 第二阶段，默认关闭 |
| 文案 | VLM | 生成文本 | 文本检索/解释 | 与以图搜图分开 |

### 为什么不直接换更大的 CLIP

CLIP 的强项是图文对齐和语义；它不会因为放大模型就变成：
- 人脸身份模型
- 近似重复检测器
- 局部物体匹配器

### 为什么不是一上来上 SSCD

SSCD 在 copy detection 上明显强于普通自监督特征（论文报告在 DISC2021 上大幅优于 SimCLR 等基线），但当前没有现成可用的 ONNX 模型与稳定打包路径。首版先用 dHash/pHash 覆盖高价值场景，SSCD 作为后续增强。

### 为什么不是用 VLM 文案做以图搜图

文案是有损中间表示：
- 会漏掉构图、姿态、局部细节；
- 会幻觉；
- 每张图生成成本高；
- 两个视觉上几乎相同的图可能得到不同文案。

VLM 适合“文本索引”和“可解释描述”，不适合替代视觉相似度。

## 4. 存储设计

当前 `ai_vectors` 的 `resource_id` 是主键，只能存一种向量。需要升级为多模型/多类型：

```text
ai_embeddings(
  resource_id,
  kind,          -- clip / dino / face
  model_id,
  dim,
  vector BLOB,
  source_path,
  updated_at,
  PRIMARY KEY(resource_id, kind, model_id)
)

ai_hashes(
  resource_id PK,
  dhash INTEGER,
  phash INTEGER,
  updated_at
)

ai_faces(
  id,
  resource_id,
  face_index,
  bbox_json,
  embedding BLOB,
  detector_score,
  model_id,
  updated_at
)
```

- `ai_vectors` 迁移到 `ai_embeddings(kind='clip')`，保留兼容读取；
- CLIP 与 DINO 可分别重建；
- 人脸表按脸存，不按资源存；
- 不引入新向量库，继续 NumPy 暴力检索。

## 5. 索引流程

```text
active image
  ├─ CLIP encode
  ├─ DINOv2 encode（可选/可关闭）
  ├─ dHash/pHash
  └─ 人脸检测/embedding（可选）
        ↓
  ai_embeddings / ai_hashes / ai_faces
```

- 索引任务分阶段：CLIP → hash → DINO → face；
- 每个阶段独立状态，失败不影响已有 CLIP 搜索；
- 模型或 prompt 版本变化时按版本重建；
- 外部图片查询不写入索引，只做一次性查询。

## 6. 查询流程

```text
选择图片（resource 或外部文件）
  → 读取 query 向量/hash
  → 硬过滤（active image、可选类型/时间/分类）
  → 排除自身
  → 模式：
      duplicate: Hamming 距离
      semantic: CLIP cosine
      visual: DINO cosine
      person: ArcFace 最大脸相似度
  → 归一化/排名
  → 综合模式用 RRF 融合
  → topK 返回
```

### 综合排序

不要直接相加 CLIP/DINO 原始分数。用 Reciprocal Rank Fusion：

```text
score = Σ 1 / (k + rank_i)
```

再单独把 `pHash` 命中置顶。这样不会因为两个模型分数尺度不同而失真。

## 7. API

```text

GET  /ai/similar?resourceId=49&mode=duplicate

  multipart image
  mode / limit
```

响应：

```json
{

  "indexed": 236,
  "matched": 236,
  "returned": 30,
```

## 9. 评估

固定查询集：

- 连拍/同场景：文件名相邻、时间接近；
- 同一套服装/同一场景：人工标注；
- 同一个人不同服装：人工标注；
- 近似重复：缩放/压缩/裁剪；
- 随机负样本。

指标：

- Recall@10/20
- mAP
- duplicate precision/recall
- person precision@10
- 查询延迟、索引耗时、内存

先测 CLIP 单模、DINO 单模、RRF 混合，不凭感觉选模型。

## 10. 性能与容量

- 236 张：当前 CLIP 索引约 40 秒；DINO 额外约 40 秒；hash 忽略不计。
- 1 万张：CLIP 约 7 分钟、DINO 约 30 分钟（当前单进程）；可分批/后台。
- 5 万张：只保留 CLIP + hash；DINO 可选；人脸另算。
- 50k × 512 float32 ≈ 100 MB；50k × 384 ≈ 77 MB；暴力矩阵乘法仍可接受。
- 不先上向量库；超过 5 万再评估 sqlite-vec/FAISS/LanceDB。

## 11. 分阶段

### P1：CLIP + 近似重复

- 查看器/Inspector 入口；
- `/ai/similar`；
- CLIP cosine + dHash；
- 排除自身、模式分组、计数；
- 不新增模型。

### P2：DINOv2 A/B

- 增加 24 MB 量化模型；
- 索引 + 视觉模式；
- 用固定查询集对比 CLIP/DINO/RRF；
- 只有指标提升才默认启用。

### P3：同一个人

- SCRFD + ArcFace；人脸检测/embedding；
- 默认关闭，用户明确开启；
- 只本地存储 embedding；
- 单独模式，不混入综合分数。

### P4：局部/物件

- YOLO/SAM 框选或裁剪；
- 局部 CLIP/DINO；
- 外部图片查询；
- 视频关键帧。

## 12. 风险

- 人脸是敏感数据，必须 opt-in、可删除、不可默认上传；
- CLIP/DINO 分数不可跨查询直接比较，需相对排序；
- 近似重复阈值需要按数据校准；
- 外部图片查询要限制文件大小/格式；
- 多模型索引会显著增加后台耗时，必须分阶段任务；
- 不能把“同一次拍摄”误称为“同一个人”。

## 14. 推荐

先做 P1，不要等 VLM/DINO/人脸全部齐备。P1 就能覆盖“同一次拍摄/近似重复”的主要需求；P2 用数据决定 DINO 是否值得默认开启；P3 再谨慎引入人脸。以图搜图的核心是**分模式 + 多信号**，不是再找一个更大的 CLIP。

## 15. 其他可选方案与取舍

### 15.1 连拍/会话分组（最高性价比）

同一拍摄会话通常有：

- 文件名连号；
- EXIF/文件时间接近；
- 相同尺寸/相机；
- 相同场景和人物。

先按时间窗（例如 120 秒）+ 文件名序列聚合，再在会话内用 CLIP/DINO 排序。它不需要新模型，对“同一次拍摄”比单纯全库向量更准。

结论：应加入 P1，作为**候选集收缩**，不是替代向量检索。

### 15.2 SSCD（更适合近似重复）

SSCD 是专门为 copy detection 训练的描述子，论文报告在 DISC2021 上明显优于普通自监督特征。相比 pHash：

- 对裁剪、压缩、叠加文字更稳；
- 仍是全局描述子，不做人脸/语义；
- 当前模型是 TorchScript/Transformers，需要先导出 ONNX；不能作为首版依赖。

结论：如果“近似重复”是核心需求，P2 应优先评估 SSCD，而不是只依赖 pHash。

### 15.3 DINOv3

DINOv3 已提供 ViT-S/16 ONNX，视觉特征比 DINOv2 更新；但：

- 权重许可证是 `license:other`，需要单独确认商用/再分发；
- 当前没有本地基准，不能直接假设优于 DINOv2；
- 模型更大，打包/推理成本更高。

结论：做 A/B 候选，不先替换 DINOv2-small。

### 15.4 关键点/几何验证

SuperPoint + LightGlue 或 SIFT + RANSAC 可以验证：

- 同一物体/同一场景的局部几何；
- 裁剪、旋转、透视变化；
- 近似重复的误报过滤。

它比全局向量更精确，但每对图成本高。适合只对 top 20 做 **rerank**，不适合全库索引。

### 15.5 VLM 重排

Qwen2.5-VL / Florence-2 可以比较查询图和候选图：

- “这两个人是不是同一人/同一套衣服？”
- “这张图是否包含同一件红帽子？”
- “构图/姿态是否接近？”

适合 topK 重排，不适合每张图全库比较。它解决语义和关系，不解决精确几何/人脸。

### 15.6 局部/多裁剪检索

全图向量会被背景稀释。可对：

- 人物框；
- 衣服/帽子框；
- 手部/物件；
- 图像中心裁剪；

分别取 CLIP/DINO 向量，查询时按区域匹配。它更适合“找同款帽子/同一件衣服”，但需要检测/分割和更多存储。

### 15.7 用户反馈与学习融合

记录用户点击、停留、二次选择，学习：

- 当前用户更看重人脸、服装还是场景；
- 不同模式的权重；
- 个人库的“相似”定义。

首版先手工 RRF；有足够点击后再做轻量学习排序，不要一开始训练。

### 15.8 不适合作为主方案的选项

| 方案 | 为什么不先做 |
|---|---|
| 只换更大 CLIP | 不解决人脸、重复、局部物件 |
| 只用 VLM 文案 | 有损、幻觉、成本高，丢失构图细节 |
| 只上向量数据库 | 解决规模，不解决相似定义/质量 |
| 只用 pHash | 对连拍和裁剪不够 |
| 全库关键点匹配 | 成本过高 |
| 人脸默认开启 | 隐私和误识别风险 |

### 15.9 修正后的推荐路线

```text
P0  CLIP + pHash + 时间/连拍会话收缩
P1  DINOv2-small 视觉模式（A/B 后决定）
P2  SSCD 或关键点 topK 重排（重复/裁剪）
P3  人脸同一个人（opt-in）
P4  局部裁剪 + VLM rerank
```

如果只问“现在最值得补的是什么”：**连拍会话收缩 + SSCD/pHash 的重复通道**。  
如果问“准确性上限最高的是什么”：**人脸 + 局部裁剪 + VLM topK 重排**，但成本和隐私代价最高。

### 16.1 VectorGallery 的具体做法

代码里实际有：

```text
search_by_text
search_by_image_path
search_by_image_data
search_by_image_object
search_multimodal_late_fusion
```

融合参数：

```text
fusion_method = rrf | weighted
rrf_k = 60
text_weight = 0.5
image_weight = 0.5
candidate_multiplier = 5
min_candidate_k = 100
```

这说明“图文融合”不是把文本和图片向量直接相加，而是**分别检索后做 RRF/加权融合**。这一点应吸收。

### 16.2 MaterialSearch 的结论

它最接近我们的产品目标：Chinese-CLIP、图片搜图片、文字搜图片、视频检索、Windows 整包。但：

- 许可证是 GPL-3.0，不能把代码直接并入当前项目；
- 核心逻辑已拆到独立包，且部分代码混淆；
- 部署形态是 Web/Windows bundle，不是 Electron 内嵌。

因此只参考产品能力与打包策略，不复制代码。

### 16.3 deep-semantic-search 的结论

它提供了完整的：

- SigLIP 图片向量 + USearch；
- 图片搜图片、文字搜图片；
- 重复图检测；
- Florence-2 caption；
- 图片聚类。

但依赖 `torch`、SigLIP SO400M（1152 维）、BGE-M3、Florence-2，模型和运行时都远重于当前 ONNX 方案。可借鉴分层接口和 duplicate threshold，不引入其运行时。

### 16.4 grape 的结论

它的 README 明确写了：

> `--like` matches semantics, not pixels. For actual duplicate detection, use perceptual hashing.

这与我们的判断一致：**CLIP/DINO 做语义相似，pHash/dHash 做重复检测**。它的缓存按文件 stat + model 失效，也值得借鉴。

### 16.5 最终选择

不 fork 任何一个项目。采用：

```text
Electron 桌面端
  → FastAPI（现有）
  → SQLite（现有业务库 + ai_embeddings/hash）
  → NumPy 本地检索（236–5k）
  → 可选 DINOv2-small ONNX
  → pHash/dHash
  → 人脸 opt-in
```

吸收：

- VectorGallery 的**图片查询 API + RRF 融合 + 候选倍数**；
- grape 的**语义相似与重复检测分离 + 文件缓存失效**；
- deep-semantic-search 的**Indexer/Searcher 分层 + duplicate threshold + captioner 接口**；
- MaterialSearch 的**中文素材库产品目标**，但不使用其 GPL 代码。

暂不采用：

- Qdrant/Flask/FastAPI 三服务编排；
- Torch + SigLIP SO400M + BGE-M3；
- 全库关键点匹配；
- 默认人脸识别；
- 用 caption 替代视觉向量。

**选择结论：P1 先实现“CLIP 以图搜图 + dHash 重复图 + 连拍会话收缩”；P2 再以 DINOv2-small 做 A/B；P3 才考虑 SSCD/人脸/局部裁剪。**

实际实现：

- Next.js UI + 独立 Python 推理服务；
- `jina-embeddings-v4`（Qwen2.5-VL 架构，2048 维）；
- SQLite + `sqlite-vec`，不是 Qdrant；
- 向量分成 `title_vectors` / `description_vectors` / `image_vectors` 三张表；
- 支持文本搜索、上传图片搜索、已有图片找相似、向量目标多选；
- AI 分析使用 `glm-4.6v-flash` 远程模型生成 title/description/tags；
- 索引迁移有 `model_migrations` 与 `*_vectors_new` 临时表。

值得吸收：

- **多向量类型**：标题、描述、图片各一张向量表，查询可选目标；
- **图片上传搜图**：`/search/unified/image` 的接口形态；
- **模型迁移**：旧/新模型向量并存、迁移表、可恢复；
- **sqlite-vec**：当数据超过 1 万时，是比引入 Qdrant 更轻的候选。

不应照搬：

- Jina v4 2048 维模型对当前 Electron/Python 3.14 包体和 CPU 都过重；
- 独立推理服务增加部署复杂度；
- 远程 GLM 分析不符合“全部本地”的第一目标；
- 它的“AI 描述”主要来自远程 API，不是本地 VLM。

### 17.2 VimgFind（AGPL-3.0）

实际实现：

- Python tkinter + ONNX Runtime；Windows/macOS 桌面应用；
- Chinese-CLIP 512 维，图片/文本双编码；
- HNSW（hnswlib）索引，默认容量 100 万，索引约 1 MB / 400 张；
- 可切换模型：Chinese-CLIP、DINOv2-base（768 维）、OSNet（512 维）、ResNet50（2048 维）、EfficientNet；
- 每个模型独立索引；模型注册表带 SHA-256、尺寸、预处理、tokenizer 配置；
- 图片输入支持文件、剪贴板、拖放；支持多图懒加载搜索；
- 过滤阈值、文件类型、大小、目录、去重；
- 后台多线程索引，排除规则。

最关键的借鉴：

- **OSNet 人物再识别**：比单纯 CLIP 更适合“同一个人/同一套造型”，尤其全身/遮挡场景；
- **每模型独立索引**，而不是把所有模型塞进一个向量表；
- **模型注册表**：模型、预处理、维度、索引参数都配置化；
- **图片输入三入口**：文件、剪贴板、拖放；
- **HNSW 作为规模化候选**，但当前 236 张不需要。

不应照搬：

- AGPL-3.0，不能复制代码到当前项目；
- tkinter UI 不适用；
- HNSW 全量内存索引对 236 张是过度设计；
- 多模型全量索引会让磁盘/内存/索引时间成倍增长，必须按需启用。

### 17.3 追加后的判断

| 能力 | 选择 |
|---|---|
| 默认图搜图 | 现有 CLIP 512 维 |
| 近似重复 | dHash/pHash |
| 同一次拍摄 | 时间/连拍会话 + CLIP |
| 视觉相似 | DINOv2-small，A/B 后决定 |
| 同一个人/造型 | OSNet 优先，人脸 ArcFace 可选 |
| 多向量 | 采纳 `image/caption/ocr` 分 kind 存储，不采用 Jina v4 |
| ANN | 1 万以下 NumPy；1 万以上评估 sqlite-vec/HNSW |
| 模型管理 | 采纳模型注册表、每模型独立索引 |
| 图片输入 | 文件、剪贴板、拖放 |
| 部署 | 保持 Electron + FastAPI + SQLite，不引入 Next.js/Qdrant |

### 17.4 修正后的落地顺序

```text
P1  CLIP 图搜图 + dHash + 连拍会话
P2  DINOv2-small 视觉模式 A/B
P3  OSNet 人物/造型相似（可选）
P4  SSCD 或关键点 topK 重排
P5  sqlite-vec/HNSW（数据量触发）
P6  本地 VLM caption/重排（独立能力）
```

这次追加参考后，**最终选择仍是本地混合方案，但把 OSNet 提到了人脸之前**：  
对 cosplay/全身照，“同一个人/同一套造型”用 OSNet 通常比人脸更稳；人脸只在用户明确需要且正脸足够时启用。

### 17.5 明确不选

- 不采用 Smartlmager 的 Jina v4 + 独立推理服务；
- 不采用 VimgFind 的 AGPL 代码；
- 不采用 MaterialSearch 的 GPL 代码；
- 不在 236–5k 阶段引入 Qdrant、HNSW 或 sqlite-vec；
- 不把标题/描述向量当成图片视觉相似的主信号。

**最终方案：CLIP 语义图搜图 + dHash 重复图 + 连拍会话；DINOv2-small 做视觉 A/B；OSNet 做人/造型相似；人脸仅在 opt-in 时补充。**
