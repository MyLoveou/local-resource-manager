# 全项目性能 · 实现方案

> 状态：**已定稿 / 实现中**  
> Feature ID：`app-performance`  
> 与 OpenSpec `design.md` 同范围

## 目标 / 不交付

与 [`需求.md`](./需求.md) 一致。沿用现有分层：`shared/db`、`library` 仓储/用例、renderer `infrastructure/http` + 组件。禁止平行新框架。

**不交付：** 把 FastAPI 部署到公网、对象存储、上传 API、token 强制校验（可另切片）、把入库 IO 下放到渲染进程。

## 总原则：客户端可以快，真相在 API

```
[渲染进程]  显示、虚拟列表、草稿、缓存、乐观 UI
     │ HTTP（唯一业务通道）
[FastAPI]   查询、事务、导入 job、文件流
     │
[SQLite + 库目录]
```

- **可以抛弃「每次操作都等后端」的，只有交互**：点选高亮、标签输入草稿、网格滚动位置。写入仍一次 PATCH。
- **不能抛弃后端的：** 任何会改变库目录或 SQLite 的事，以及读库内媒体。否则以后服务器部署要推翻重来。
- 本地现在用路径导入；服务器以后用上传。**导入入口可变，ImportService 与资源包布局不变。**

## 阶段（必须按序）

| 阶段 | 内容 | 出口 |
|------|------|------|
| **S0 测量** | 列表/详情/导入/滚动；若有语料补「千级」 | 一页数字 |
| **S1 数据库** | 复合索引；`_hydrate` 一次加载；列表 **slim DTO + keyset**；stats 降成本 | pytest + EXPLAIN |
| **S2 大批量导入** | 进程/线程池做 hash·copy·probe·thumb；**单队列写库**；job 不占用请求线程；进度轮询；导入中 GET 列表仍通 | 导入时窗口可点 |
| **S3 HTTP** | FileResponse 缓存头；`/content` 日志降级 | 缩略图可缓存 |
| **S4 万级显示** | 虚拟网格只挂可视格；列表不 hydrate 重字段；lazy + 缩略图；词表不挡；bump 局部；axios 降噪；DevTools 默认关 | 万级滚动不卡死（可用合成数据测） |
| **S5 查看器** | resize 防抖、拖拽、打开后 content、±1 预取 | 原 image-consume-perf |
| **S6 数据卫生** | 维护脚本：全量清空；无缩略图补生成或删除 | 脏库可清干净后再导入 |

S0 未完成不得声称后面阶段完成。S6 在 S2 缩略图路径稳定之后执行，避免清完又用旧逻辑导入出脏数据。

## 与现有架构的取舍

| 候选 | 决定 |
|------|------|
| 前端直接 `fs` / IPC 写库 | **否**（基线 + 远期服务器） |
| 导入并发无上限 | **否**；CPU `min(4, CPU-1)`，SQLite **单写者** |
| 万级一次 `GET` 全表 | **否**；keyset 分页 + 前端只保留已加载页（可累计到 10k 轻量行，禁止 10k 详情） |
| 清空库做进启动 | **否**；显式脚本/命令 |
| Redis / 换 DB | **否** |

## 分主题设计

### A. 大批量导入（防卡死）

现状：`run()` 里对 `candidates` **逐个 await `_ingest_one`**；整个 `run` 若绑在一个 HTTP 请求上，请求结束前事件循环被占满。

目标链路：

1. `POST` 只创建 job、收下路径列表（路径很多时注意 JSON 体积；超大目录由后端 `collect`，前端只传根路径）。
2. 后台 task 跑导入；前端轮询已有进度接口。
3. **工人池**：hash / copy / probe / Pillow / ffprobe 进 `asyncio.to_thread` 或 `ProcessPoolExecutor`（Pillow/hash 释放 GIL 用线程即可；ffprobe 子进程已隔离）。
4. **写库单一协程**：工人只产出「待写入事实」，避免多协程抢同一 `AsyncSession`。
5. 每 N 条 `await asyncio.sleep(0)` 或自然 await，保证 `/library/resources` 能插队。
6. 缩略图失败：**不让原图顶上网格**（列表只认 thumbnailPath）；失败记录进 job，S6 再清。

卡死的三层都要拆开：事件循环（HTTP）、SQLite 写锁、渲染进程（不要 `await` 一次导入结束才关向导；向导只订阅进度）。

### A2. 展示面：缩略图 vs 原图

统一入口（建议 `resolveCardImageUrl(resource)` 一处）：只返回缩略图 URL 或空。`ImageViewerOverlay` 是唯一允许拼 `/content` 的组件。

改掉 `thumbnailPath ?? coverPath`。`Card` / `InfoPanel` / `EditResourceModal` / 概览卡片都走同一函数。

### B. 万级前端显示（防卡死）

现状：`useResourcePage` limit 80 + 触底追加；`VirtualGrid` overscan 4。风险是：追加到 10k 后 **items 数组很大但尚可**；若每张卡带重组件/原图 URL/点选触发整表 reset，会卡。

约束：

| 层 | 做法 |
|----|------|
| API | 列表字段只要网格需要的：`id, title, thumbnailPath, type, status`；不要 files/todos/描述长文 |
| SQL | `WHERE status=? AND type=? ORDER BY created_at DESC, id DESC` 走复合索引；**keyset** 深页，不用 `OFFSET 8000` |
| DOM | 只渲染可视 + overscan；卡片 `loading=lazy`；无缩略图占位；**禁止** `coverPath`/`/content` 当封面 |
| 内存 | 详情 Map 按 id，上限淘汰（如 50）；词表全局一份 |
| 失效 | bump 时已加载窗口用 keyset 重拉当前窗口，或只补丁一条，禁止无脑 `items=[]` 再从 offset 0 拉一万次 |
| 点选 | 浏览模式不要拖拽选择逻辑误伤；信息栏用缩略图 |

万级验收允许用脚本插入 10000 条「假资源 + 小缩略图」，不必真导入 10000 张 4K。

### C. 数据卫生（优化后清脏）

当前脏的典型：资源已复制、缩略图失败，网格退回 cover/原图。

两种工具（都**显式调用**，不进开机）：

1. **`reset_library`（清空）**  
   停应用 → 删除 SQLite 文件与 `library_store` 目录 → 下次启动跑迁移得到空库。  
   给本次优化后的开发库用。文档写清路径（`settings.db_path` 旁）。

2. **`repair_thumbnails`（可选，清库前可先跑）**  
   扫描 `role=thumbnail` 缺失或文件不存在 → 尝试 `put_thumbnail` → 仍失败则 **删除该资源包与 DB 行**（开放问题未反对时）。

S6 默认流程：**先合并新导入/缩略图代码 → 再 reset 空库 → 用户重新导入**。不在优化过程中途自动删用户未确认的数据。

## 数据流

**列表** keyset GET slim → 虚拟格 + lazy 缩略图（缓存头）。  
**点选** 内存详情 → 否则 GET hydrate 一次 → 面板缩略图。  
**导入** POST job → 工人 CPU → 单写者 SQLite → 轮询进度。  
**看图** 打开才 content。  
**卫生** 停进程 → reset 或 repair → 再启动。

## 风险

| 风险 | 缓解 |
|------|------|
| 前端直写库图一时快 | 禁止；与服务器部署冲突 |
| 导入工人过多打满磁盘 | 工人上限 4；写库 1 |
| 万级 items 仍占内存 | 只存 slim 行；详情 LRU |
| reset 误删 | 脚本打印路径；须确认参数 |
| keyset 与现有 offset 客户端 | 一版内兼容或同步改 `useResourcePage` |
| 无测量就调 PRAGMA | S0 先记 |
