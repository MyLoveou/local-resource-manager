# 回收站与批量删除/恢复 · 实现方案

> 状态：**已定稿**（与 OpenSpec `design.md` 同一范围）  
> Feature ID：`library-trash`

## 目标 / 不交付

与 [`需求.md`](./需求.md) 一致。沿用 `library` + 现有 `DELETE` 软删 + `Resource.restore()`，**不**新建回收站表、不新分层。

## 与现有架构的取舍

| 做法 | 为何 |
|------|------|
| `status=trashed` + `deleted_at` | 数据模型已定；不建 trash 表 |
| 新 `restore` / `purge` / `batch`，不改 DELETE 语义 | D-20260912-01：DELETE 仍是软删 |
| 彻底删走 `FileOps.remove_tree(package.root)` | 包路径只在 ResourcePackage 内拼；只删库内副本 |
| 扩展 selection store 为多选 | 已有单击选中；禁止再做一套列表状态 |
| `useResourcePage` 的 `type` 可空 | 回收站混排；类型页仍传 type |
| 库 revision 在 trash/restore/purge 后 bump | 修删除后网格不刷新 |

## 模块边界

```
类型页/回收站网格  → 多选 selection + 批量条
InfoPanel         → 按 status 显示 移入 / 恢复+彻底删除
HTTP              → 已有 DELETE；新增 restore、purge、batch
LibraryQueryService → trash / restore / purge / batch
ResourceRepository  → restore、purge（删行）、list(status)
ResourcePackage     → purge 时 remove_tree(root)
```

## 数据流

**移入**  
确认 → DELETE 或 batch trash → `to_trash()` → bump → 类型页 reset（无该 id）。

**恢复**  
确认 → POST restore → `restore()` → bump → 回收站无、类型页有。

**彻底删除**  
确认 → POST purge → `remove_tree(package.root)` → DELETE 行 CASCADE → bump。包删失败则**不** DROP（避免库有记录、盘已空或盘有文件库已无）。若包已不存在，允许只 DROP。

**批量**  
一次事务外逐条（单条失败不影响其他）或每条独立 commit。推荐**逐条独立提交**，与部分失败契约一致。

**错误**  
404：单条 restore/purge。批量进 failed。非法 action → 422。

## 风险

| 风险 | 缓解 |
|------|------|
| purge 先 DROP 后删盘失败变孤儿包 | 先删盘成功或包已不存在，再 DROP |
| 多选手势 | 须点「批量删除/选择」进模式后再点选；取消退出 |
| 清空回收站 ids>200 | 前端按页拉齐再分批 batch，或后端 purge_all 仅清空接口；本轮前端循环 batch |
