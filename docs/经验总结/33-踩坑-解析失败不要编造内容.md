# 33 · 踩坑：解析失败不要编造内容

> 来源：番剧 `D-fragments` 导入后被改名成 `273`。

## 现象

```
title = "273"
source_name = "D-fragments"      ← 导入时的源名称是对的
scraped_source = "mikan:273"     ← 应用了蜜柑的候选
```

`273` 正是蜜柑的番剧 ID。

## 根因链

```python
# mikan.py（旧代码）
if not title:
    title = ident        # ← ident 就是 "273"
```

1. 蜜柑详情页没解析出 `og:title` / `<h1>`（页面被拦截或结构变化）
2. 兜底直接拿**数字 id 当标题**
3. 同时 Bangumi 不可达，"用 Bangumi 标题覆盖"这条退路也断了
4. `apply()` 里 `resource.title = detail.title` **没有空值保护**，于是 `273` 落库

另外一处同源问题：Open Graph 的正则要求 `property` 写在 `content` **之前**

```python
# 旧：content 在前的写法完全匹配不到
r'<meta\s+property=["\']og:title["\']\s+content=["\']([^"\']+)["\']'
```

实测两种写法：`property` 在前 → 解析成功；`content` 在前 → 标题和封面全空。

## 修法

1. 解析不出就**留空**并 `logger.warning` 带上 id，绝不拿 id 冒充内容。
2. `apply()` 对空值一律跳过（标题、作品档案都已加）。
3. 解析 `<meta>` 改成先抓标签再取属性，**不依赖属性顺序**。

## 教训

1. **兜底值必须是"无"，不能是"看起来像数据的 id/序号"**。空值能被发现，假数据会被当真。
2. 写入侧要有空值闸门：解析层返回空不可怕，`apply` 无脑覆盖才是事故。
3. 解析 HTML 别假设属性顺序；要么上解析器，要么按属性名取。
4. 这类 bug 只在「解析失败 + 上游不可用」同时发生时暴露，本地很难复现——所以**要用构造样本做单测**（两种属性顺序各一条）。
