# 30 · 经验：文件规模门禁下的落点选择

> 来源：本仓 `pnpm check:file-size` 有硬规则——基线文件不得继续增长，新增文件不得超 500 行。它多次改变了实现落点。

## 现象

给「播放进度」和「智能导入」加功能时，被连续拦下三次：

```
repositories_resources.py: 1668 行，超过基线 1663
import_service.py: 834 行，超过基线 828
ai/application/service.py: 1230 行，超过基线 1227
schemas.py: 534 行，超过目标 500
```

## 处置顺序（按成本从低到高）

| 做法 | 例子 |
|------|------|
| 换落点，不加行 | 分类建议挂在 `api/router.py` 而不是 `service.py`（api 层没有基线压力） |
| 把 DTO/子功能挪进功能目录 | 建议相关 schema 放进 `smart_import/schemas.py`，公共 `schemas.py` 回落到 500 以内 |
| 先拆分再挂调用 | 缩略图登记逻辑从 `import_service.py` 移到 `thumbnails.py`，-65 行，再挂 pipeline |
| 压缩写法 | 6 行的元组循环压成 1 行，正好回到基线 |

## 一个反直觉的点

**"基线文件不能增长"并不等于"不能改它"**。正确姿势是：改之前先算出还有多少余量：

```
当前行数 vs scripts/file-size-baseline.json
```

只有 1 行余量时，任何"顺手加点注释"都会让门禁变红。所以要么先拆分腾地方，要么把改动放到不增长的文件里。

## 教训

1. **先看门禁再决定写哪里**，不要写完再被动拆分。
2. 拆分要顺手、要有边界（缩略图登记是独立职责），不是为凑行数硬切。
3. 「大改顺手拆分」是项目明确鼓励的，拆分本身可以是一个提交的前半段。
4. 新增文件比改基线文件安全；功能内聚的 DTO 放功能目录比塞公共文件好。
