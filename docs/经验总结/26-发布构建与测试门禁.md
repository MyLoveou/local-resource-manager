# 26 · 发布构建与测试门禁

> 本文解释 `pnpm release:win` 到底做了什么、CI 如何复现、验证脚本检查什么，以及一次发布失败应该按什么顺序排查。
> 主要代码：`scripts/release.mjs`、`scripts/verify-release.mjs`、`scripts/copy-ffprobe.mjs`、`.github/workflows/release-windows.yml`、`apps/desktop/electron-builder.yml`、`apps/backend/packaging/`。

## 1. 发布不是“跑一下 electron-builder”

本项目的发布是一条串行质量门禁：

```text
清理旧产物
  → TypeScript 类型检查
  → ESLint
  → 后端 pytest
  → 前端 electron-vite build
  → PyInstaller 冻结后端（onedir）
  → 复制 ffprobe
  → electron-builder 生成 NSIS + zip
  → 验证产物与后端冒烟
  → 生成 SHA256SUMS
```

任何一步失败都会 `exit 1`，后续步骤不会执行。这样避免“安装包有了，但后端起不来”。

```mermaid
flowchart LR
  A["清理 release / build / dist"] --> B["typecheck"]
  B --> C["lint"]
  C --> D["pytest"]
  D --> E["electron-vite build"]
  E --> F["PyInstaller onedir"]
  F --> G["copy ffprobe"]
  G --> H["electron-builder<br/>NSIS + zip"]
  H --> I["verify-release<br/>health + latest.yml + hash"]
  I --> J["release/ 产物"]
```

入口：

```bash
pnpm release:win
```

实现在 `scripts/release.mjs`。

## 2. 本地发布流程拆解

### 2.1 清理

```js
for (const dir of ['release', 'apps/backend/build', 'apps/backend/dist']) {
  rmSync(join(ROOT, dir), { recursive: true, force: true })
}
```

清理是必要的：

- `release/` 里可能残留上一版本安装包；
- `apps/backend/dist` 可能残留旧后端；
- `apps/backend/build` 的 PyInstaller 缓存可能包含旧依赖。

### 2.2 质量门禁

```js
run('类型检查', 'pnpm', ['--filter', 'desktop', 'typecheck'])
run('Lint', 'pnpm', ['--filter', 'desktop', 'lint'])
run('后端测试', python, ['-m', 'pytest', '-q', 'tests'], {
  cwd: 'apps/backend',
  shell: false,
})
run('前端构建', 'pnpm', ['--filter', 'desktop', 'build'])
```

注意：

- `pytest` 的 cwd 是 `apps/backend`，不是仓库根目录。
- 使用 `.venv` 里的 Python，不是系统 Python。
- 当前 lint 有大量历史 warning，但 0 error；release 以退出码为准。若要收紧，可加 `--max-warnings 0`，但要先清理存量。

### 2.3 冻结后端

```js
run(
  '冻结后端',
  python,
  ['-m', 'PyInstaller', '--noconfirm', '--clean',
   '--distpath', 'apps/backend/dist',
   '--workpath', 'apps/backend/build',
   'apps/backend/packaging/backend.spec'],
  { shell: false }
)
```

产物是 **onedir**：

```text
apps/backend/dist/source-manager-backend/
├─ source-manager-backend.exe
├─ _internal/
│  ├─ Python 运行时
│  ├─ 依赖包
│  └─ app/shared/db/migrations/*.sql
└─ ...
```

`migrations.py` 在冻结态从 `sys._MEIPASS` 找 SQL 文件：

```python
if getattr(sys, "frozen", False):
    MIGRATIONS_DIR = Path(sys._MEIPASS) / "app" / "shared" / "db" / "migrations"
```

如果打包后启动报“no such table”，优先检查迁移目录是否进了产物。

### 2.4 复制 ffprobe

```js
run('ffprobe', 'node', ['scripts/copy-ffprobe.mjs'])
```

视频时间线、时长、分辨率依赖 ffprobe。项目不假设用户机器装了 ffprobe，而是把 `@ffprobe-installer/win32-x64` 的二进制复制到：

```text
apps/desktop/build/ffprobe/ffprobe.exe
```

随后 electron-builder 通过 `extraResources` 放进：

```text
resources/ffprobe/ffprobe.exe
```

主进程启动冻结后端时注入：

```ts
env.FFPROBE_BIN = join(process.resourcesPath, 'ffprobe', 'ffprobe.exe')
```

### 2.5 electron-builder

```js
run('打包安装包', 'pnpm', [
  'exec', 'electron-builder', '--win', '--x64', '--publish', 'never',
], { cwd: 'apps/desktop' })
```

`--publish never` 保证本地构建不会尝试上传。上传只由 CI 的 Release 步骤做。

输出：

```text
release/
├─ local-resource-manager-0.1.2-win-x64-setup.exe
├─ local-resource-manager-0.1.2-win-x64-setup.exe.blockmap
├─ local-resource-manager-0.1.2-win-x64.zip
├─ latest.yml
├─ win-unpacked/
└─ ...
```

### 2.6 验证

```js
run('验证产物', 'node', ['scripts/verify-release.mjs'])
```

`verify-release.mjs` 会检查：

- setup.exe 存在且大于 10 MB；
- zip 存在且大于 10 MB；
- `app.asar` 存在；
- 后端 exe 存在；
- `latest.yml` 存在；
- `app-update.yml` 存在；
- `ffprobe.exe` 存在；
- `latest.yml` 的版本与 `package.json` 一致；
- `latest.yml` 的 `path` 指向当前 setup；
- `app-update.yml` 的 provider 是 `github`；
- 后端 `_internal` 目录存在；
- 启动冻结后端，30 秒内 `/health` 返回 200；
- 启动后能生成非空 SQLite 文件（迁移执行成功）；
- 最后计算 setup/zip 的 sha256，写 `SHA256SUMS.txt`。

这一步是“发布可安装性”的最后保险。

## 3. CI 如何复现本地流程

`.github/workflows/release-windows.yml`：

```text
checkout
  → pnpm 11
  → Node 24
  → Python 3.14
  → 创建 .venv
  → 安装 requirements + dev + packaging
  → pnpm install --frozen-lockfile
  → 缓存 electron-builder
  → pnpm release:win
  → upload-artifact
  → gh release create（仅 tag）
```

### 3.1 为什么 CI 要安装 dev 依赖

发布脚本会跑 `pytest`。只安装 `requirements.txt` 时没有 pytest，CI 会在测试阶段失败。

```yaml
pip install -r requirements.txt \
            -r requirements-dev.txt \
            -r requirements-packaging.txt
```

### 3.2 为什么 CI 比本地慢

- 首次下载 Python/Node 依赖；
- PyInstaller 冷启动；
- electron-builder 下载 Electron/NSIS 工具；
- Windows runner 的磁盘和 CPU 比本地开发机慢；
- 后端 198 个测试在 CI 上可能需要 7 分钟以上。

工作流 `timeout-minutes: 90` 是给冷缓存留余量，不是正常耗时。

### 3.3 产物上传

```yaml
path: |
  release/local-resource-manager-*-setup.exe
  release/local-resource-manager-*.blockmap
  release/local-resource-manager-*.zip
  release/latest.yml
  release/SHA256SUMS.txt
```

即使 `gh release create` 失败，Actions artifact 仍可下载，便于排查。

## 4. 测试分层与失败教训

### 4.1 后端测试

当前测试位于 `apps/backend/tests/`，覆盖：

- API 信封、认证；
- 资源列表/搜索/排序/回收站；
- 分类树迁移、深度、循环、删除保护；
- 合集、批量标签、导出命名；
- 图片/视频时间线、EXIF；
- 导入、系列、封面；
- 抓取候选与任务；
- 设置、工作台。

测试模式：

```text
TemporaryDirectory
  → sqlite3.connect + migrate(conn)
  → create_async_engine
  → async_sessionmaker
  → 直接调 application service
```

这样每个测试拥有独立数据库，不依赖本机 `library.db`。

### 4.2 真实故障：TestClient + lifespan

失败测试：

```python
with patch.object(settings, "db_path", self.db_path):
    with TestClient(app) as client:
        ...
```

报错：

```text
sqlite3.OperationalError: no such table: resources
```

原因：

- `TestClient` 进入时触发 app lifespan；
- lifespan 使用全局 engine/session；
- 测试只迁移了临时库，全局 app 却可能指向另一个库；
- 本地顺序执行时，其他测试可能已经把全局 engine 初始化到临时库，造成“偶尔通过”。

修复：

```python
async with self.factory() as session:
    collections = self._collection_svc(session)
    with self.assertRaises(HTTPException) as ctx:
        await collections.export(99999, str(self.root / "out"))
    self.assertEqual(ctx.exception.status_code, 404)
```

原则：**测业务规则就测服务层，不要在单元测试里启动整个应用。**

### 4.3 前端检查

```bash
pnpm --filter desktop typecheck
pnpm --filter desktop lint
pnpm --filter desktop build
```

- `typecheck`：`vue-tsc` + `tsc` 两套配置。
- `lint`：当前 0 error，仍有历史 warning。
- 存在 `imageViewer.test.ts`（Node `node:test`），但目前没有接入 npm script；这是已知测试缺口。

### 4.4 发布后验证

发布成功后至少检查：

```text
Actions success
Release public / not draft
5 个资产齐全
latest.yml version = 0.1.2
latest.yml path = setup.exe
app-update.yml provider = github
后端 /health 200
```

## 5. 打包产物为什么这么大

`setup.exe` 约 164 MB，主要组成：

- Electron/Chromium 运行时；
- Vue 构建产物；
- Python 运行时与依赖；
- PyInstaller 的 `_internal`；
- ffprobe；
- NSIS 压缩后的安装器。

这不是“代码大”，而是桌面应用把浏览器和 Python 运行时一起带上了。

优化方向（按收益/风险排序）：

1. 排除未使用的 Python 依赖，减小 `_internal`；
2. 检查 PyInstaller hidden imports 是否带入多余模块；
3. 前端按需加载，减少 asar 体积；
4. electron-builder 压缩级别（会增加构建时间）；
5. 代码签名不会减小体积，但能改善 Windows 信任体验。

不要为了体积把后端改成“用户自己装 Python”，这会把安装复杂度转移给用户，和当前“开箱即用”的目标冲突。

## 6. 发布失败排查顺序

```text
1. 看 Actions 失败的 step
2. 如果是测试失败：本地复现单个测试
3. 如果是 PyInstaller：检查冻结后端能否启动
4. 如果是 electron-builder：检查 release/ 与签名/缓存
5. 如果是 gh release：检查 tag、Release 是否已存在、权限
6. 如果 Release 成功但客户端不更新：检查 public、latest.yml、app-update.yml、版本号
```

常用命令：

```bash
pnpm --filter desktop typecheck
pnpm --filter desktop lint
apps/backend/.venv/Scripts/python -m pytest -q apps/backend/tests
pnpm --filter desktop build
pnpm release:win
```

只跑单个测试：

```bash
apps/backend/.venv/Scripts/python -m pytest -q \
  apps/backend/tests/test_batch_tag_export.py::BatchTagExportTests::test_export_missing_collection_404
```

## 7. 安全与发布纪律

- 不把 token、证书、私钥写入仓库或日志。
- `GITHUB_TOKEN` 只在 workflow 中使用，权限最小化。
- 发布前确认 `git status`，不要把本地调试文件打进产物。
- 不要修改已发布版本的 tag；需要修复就发新版本。
- 不要手工改 `latest.yml` 的哈希。
- 当前未做代码签名，Windows 可能提示未知发布者；正式分发前应配置 Authenticode。

## 8. 学习指南

### 8.1 推荐顺序

1. Git tag / GitHub Release / Actions 基础。
2. electron-builder 的 `files`、`extraResources`、NSIS、artifactName。
3. PyInstaller onedir 与 `sys._MEIPASS`。
4. 产物校验：哈希、版本清单、冒烟测试。
5. CI 缓存、超时、artifact。
6. 代码签名与供应链安全。

### 8.2 推荐资料

- electron-builder：<https://www.electron.build/>
- NSIS：<https://nsis.sourceforge.io/Docs/>
- PyInstaller：<https://pyinstaller.org/en/stable/>
- GitHub Actions：<https://docs.github.com/en/actions>

### 8.3 动手练习

1. 在本地故意改错 `package.json` 版本，观察 `verify-release` 是否拦截。
2. 删除 `release/latest.yml`，看 verify 的报错顺序。
3. 只启动冻结后端，访问 `/health`，确认数据库文件生成。
4. 把 `ffprobe.exe` 移走，观察视频时间线/打包校验的变化。
5. 在 CI 中制造一个测试失败，确认 artifact 是否仍上传。
