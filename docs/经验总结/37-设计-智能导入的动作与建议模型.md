# 37 · 设计：智能导入的动作与建议模型

> 来源：`smart-import` S1。目标不是「导入时自动跑 AI」，而是「导入时给可解释的候选，用户决定是否采纳」。

## 三个概念

```python
@dataclass(frozen=True)
class ActionContext:          # 动作的输入，全部来自导入期可得信息
    resource_id: int
    type: ResourceType
    file_stem: str
    dir_name: str | None
    existing_categories: tuple[str, ...]

@dataclass(frozen=True)
class Suggestion:             # 一条建议
    field: str                # title / category / season / episode / aiAnalysis
    value: dict | None
    confidence: float         # 0–1
    reason: str               # 没有理由的建议不展示
    source: str = "rule"      # rule / scrape / ai / history
```

动作按类型注册，新类型只加模块、不改导入主流程：

```python
class CleanTitleAction:
    field = "title"
    applies_to = frozenset({VIDEO, ANIME, AV, IMAGE})
    def evaluate(self, ctx) -> list[Suggestion]: ...
```

## 数据落点

```sql
-- 0032
ALTER TABLE resources ADD COLUMN source_name TEXT;   -- 原始文件名/目录名
CREATE TABLE import_suggestions (
  id, resource_id, job_id, field, value, confidence, source, reason,
  status  -- pending / accepted / rejected
);
```

建议**持久化**而不是放内存，理由：审阅入口有两个（导入向导内 + 稍后「待审阅」），导入后关掉向导也不能丢。

`source_name` 单独一列而不是塞 `extra`：改名后要能按源名称检索、能导出、能回滚。

## 建议的产出与消费

```
导入任务（不暂停）
  → 每个资源落库后调 suggest_after_ingest()
      → 按类型取动作 → 产出建议（失败只记日志，不中断导入）
  → import_suggestions 落库 pending

审阅
  → GET 按 (field, value) 分组；组置信度取组内最小值
  → 前端 ≥0.85 默认勾选，0.5–0.85 展示不勾，<0.5 折叠
  → POST apply 逐条写回 resources.title，空值跳过
```

**组置信度取最小值**是刻意的保守：一组里只要有一条拿不准，整组就不该算高置信。

## 三个刻意的约束

1. **导入任务不暂停**：审阅发生在任务跑完之后。给任务加"等待确认"态会连带影响监视目录自动导入（那条路径没人坐在那里点确认）。
2. **采纳只改库内字段**，不动磁盘文件名——与「换封面不替换主文件」是同一类原则。
3. **动作失败不得中断导入**：`pipeline.evaluate` 里每个动作包了 try/except，坏一个动作不影响其它。

## 教训

1. 建议类功能的第一性问题是「**谁来做决定**」。一旦决定权在用户，就必须有理由、置信度、可批量、可忽略。
2. 「可解释」不是锦上添花：没有 `reason` 的建议等于让用户盲选。
3. 持久化建议 + 稳定的分组键（field+value），才能同时支撑"向导内"和"事后"两个入口。
4. 批量场景要按建议值分组，不能一项一行；还要有单次上限，避免上千行同时渲染。
