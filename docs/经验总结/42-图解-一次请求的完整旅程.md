# 42 · 图解：一次请求的完整旅程

> 用一条请求串起所有层。看懂了这一篇，就知道每层在哪、谁调谁、错在哪一层。

## 1 三个进程的边界

```mermaid
flowchart LR
  subgraph R["渲染进程 · Chromium"]
    V["Vue 组件"] --> S["Pinia store"]
    S --> A["axios 实例"]
  end
  subgraph M["主进程 · Node"]
    W["窗口/IPC"] --> B["backend 管理器"]
    B -->|"spawn + 注入 token/port/db"| P
    W --> U["electron-updater"]
  end
  subgraph P["Python 后端 · 单进程"]
    F["FastAPI 应用"] --> MW["中间件: 日志/鉴权/信封"]
    MW --> APP["application 用例"]
    APP --> DOM["domain 规则"]
    APP --> INF["infrastructure 仓储/IO"]
    INF --> DB[("SQLite WAL")]
  end
  A -->|"HTTP 127.0.0.1:动态端口<br/>Authorization: Bearer"| F
  M -.->|"additionalArguments"| R
```

**为什么渲染层不直接连数据库**：渲染层是 Web 上下文，拿不到 Node API；而且 SQLite 单写者，必须集中到一个进程里排队。

## 2 列表请求：从点击到渲染

```mermaid
sequenceDiagram
  autonumber
  participant U as 用户
  participant C as 组件
  participant ST as Pinia store
  participant AX as axios
  participant MW as 后端中间件
  participant UC as use_cases
  participant RP as 仓储
  participant DB as SQLite

  U->>C: 打开资源库
  C->>ST: loadPage(cursor)
  ST->>AX: GET /library/resources?limit=60
  AX->>MW: + Bearer token
  MW->>MW: 校验 token（失败 401）
  MW->>UC: list_resources(...)
  UC->>RP: keyset 查询（按 id/时间游标）
  RP->>DB: SELECT ... WHERE id < cursor LIMIT 60
  DB-->>RP: 行
  RP-->>UC: 实体
  UC-->>MW: 分页结果
  MW->>MW: wrap_json_envelope → {code,status,message,data}
  MW-->>AX: 200 + 信封
  AX->>AX: 拦截器拆 data
  AX-->>ST: 数组 + nextCursor
  ST-->>C: 响应式更新
  C-->>U: 列表渲染（虚拟滚动）
```

**要点**：

- 分页用 **keyset（游标）** 不是 offset。深翻页时 offset 会越翻越慢，而且并发插入会重复/漏行。
- 信封只在中间件里包一次；`204` 跳过包裹（`_should_skip`），否则前端会拿到空 body 报错。

## 3 媒体流：为什么图片必须签名

```mermaid
sequenceDiagram
  autonumber
  participant C as 组件 img src
  participant MW as 后端
  participant AUTH as media_auth
  participant FS as 磁盘

  Note over C: img/video 发不出 Authorization 头
  C->>MW: GET /library/resources/533/files/1068/content?exp=...&sig=...
  MW->>AUTH: verify(path, exp, sig)
  AUTH-->>MW: HMAC 比对 + 是否过期
  alt 签名缺失或过期
    MW-->>C: 401（图片显示为裂图）
  else 通过
    MW->>FS: 读文件（FileResponse，支持 Range）
    FS-->>C: 206/200 字节流
  end
```

**结论**：任何拼媒体 URL 的地方都必须走 `file_content_url()` / `media_path()` / `resource_thumb_url()`，不要手拼字符串。踩过的坑见 [34](34-踩坑-两个静默的数据层陷阱.md)。

## 4 导入：为什么"复制完就返回"

```mermaid
sequenceDiagram
  autonumber
  participant U as 用户
  participant UI as 导入向导
  participant API as POST /library/imports
  participant JOB as 导入任务
  participant FS as 磁盘
  participant DB as SQLite
  participant SG as suggest_after_ingest

  U->>UI: 选目录 + 类型 + 目标库
  UI->>API: 提交
  API->>JOB: 创建任务（异步）
  API-->>UI: 202 + jobId
  loop 每个文件
    JOB->>FS: 复制 + 哈希
    JOB->>DB: 写 resources/files
    JOB->>SG: 产出建议（失败只记日志）
    SG->>DB: import_suggestions pending
  end
  UI->>API: 轮询进度
  API-->>UI: done / 已识别 N 季 · N 集 · N 特典
  Note over UI: 审阅入口有两个：向导内 / 右下角待审阅
```

**为什么建议不阻塞导入**：监视目录自动导入时没人点确认，任务卡住会堆积。

## 5 播放进度：为什么刷新后才"补上"

```mermaid
sequenceDiagram
  autonumber
  participant P as 播放器
  participant API as PUT /progress
  participant APP as progress.normalize_progress
  participant DB as SQLite

  loop 每 5 秒（节流）
    P->>API: position=123.4 duration=1440
    API->>APP: 归一化（<10s 跳过 / ≥95% 记完成）
    alt 太短
      APP-->>API: skipped
      API-->>P: 204
    else 正常
      APP->>DB: UPSERT playback_progress
      API-->>P: 200
    end
  end
  P->>API: 关闭时 flush 一次
```

**踩过的坑**：`session` 是 `expire_on_commit=False`，裸 SQL 写完再读会拿到旧实例 → 表现为"上报了但接口返回旧值"。修法是写完 `expire_all()`（见 [34](34-踩坑-两个静默的数据层陷阱.md)）。

## 6 错误在哪一层被拦住

```mermaid
flowchart TD
  REQ["请求进入"] --> T{"token 有效?"}
  T -->|否| E401["401 信封"]
  T -->|是| V{"参数校验"}
  V -->|失败| E400["400 信封 + 字段说明"]
  V -->|通过| U["用例执行"]
  U -->|业务拒绝| E4XX["ScrapeError/AIServiceError<br/>→ 对应状态码"]
  U -->|未捕获异常| E500["500 信封 + 日志堆栈"]
  U -->|成功| OK["200 信封"]
```
