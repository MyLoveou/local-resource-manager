# 32 · 经验：多来源数据不要合并成一个池

> 来源：番剧刮削「只有 Bangumi，没有蜜柑」。用户提出质疑：每个渠道不是应该各自独立吗？

## 现象

候选面板里只有 Bangumi 的结果；日志偶发 `刮削渠道失败 MikanProvider:`（冒号后为空）。

## 根因（叠了三层）

1. **合并 + 共享上限**：所有渠道的命中摊进同一个列表，再截断 20 条。先返回的渠道把后面的挤掉。
2. **跨渠道去重**：用 `hit.key` 全局去重，两站指向同一部作品时只留一条。
3. **失败不可见**：渠道异常只写 `logger.warning`，UI 上完全看不出来；而 `str(exc)` 对 httpx 连接错误是空串。

## 修法

```python
# 每渠道各自配额，互不挤占；只在同一渠道内去重
_PER_PROVIDER_CAP = 15
for provider in providers:
    found = await provider.search(query)
    seen = set()
    kept = 0
    for hit in found:
        if hit.key in seen: continue
        ...
```

前端候选列表按 `source` 分组，带渠道标题与条数；失败时把异常类型名写进消息，全部失败再加一句可操作的提示。

## 为什么一开始会合并

展示层是"一条队列 + 当前选中项"，很自然地把多来源当成一个候选池。但**数据来源的独立性**和**展示的独立性**是两件事：可以把它们放在同一个面板里，却不该让它们共用预算、共用去重键、共用错误位。

## 教训

1. 多渠道/多来源的聚合，要问三个问题：**配额怎么分？去重按谁？失败怎么显示？** 三个都答不上就别合并。
2. 上限一定要**按维度分配**，不要用一个全局数字卡多来源结果。
3. 日志里只打 `str(exc)` 常常是空的；至少加异常类型名。
4. 用户的直觉往往是对的：「每个渠道应该独立」就是正确设计，合并才是短期实现便利。
