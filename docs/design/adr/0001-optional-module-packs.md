# ADR-0001 · 可选模块包与构建裁剪

- 状态：提议
- 日期：2026-10-24
- 相关：`docs/product/module-map.md`、`docs/requirements/by-area/release-and-quality.md`、`HIDDEN_SECTIONS`

## 背景

当前安装包包含全部模块代码。`HIDDEN_SECTIONS` 只是隐藏菜单和路由，不能减小安装包，也不允许后续按需添加功能。

目标有两个：

1. 不需要的模块代码不进入安装包。
2. 用户后续可以下载并启用额外功能。

需要同时考虑：

- Electron 前端代码位于 `app.asar`，动态加载外部 JS 有安全和 CSP 约束。
- Python 后端由 PyInstaller 打成 onedir，当前是单体，模块共享数据库、路由和资源模型。
- 数据库迁移、自动更新、模块版本兼容、代码签名都要一起设计。
- 图片、视频、音频等资源类型共享资源库、查询、卡片和播放器，不能简单当作独立插件。

## 决策

采用分阶段方案，不把现有应用立即改成全模块热插拔：

1. **先建立模块注册表和模块边界**，统一菜单、路由、导入、搜索、首页、监听目录的启用状态。
2. **正式发布优先使用 Edition 构建**：图片版、影视版、下载版、完整版等，通过 Vite 条件入口和 PyInstaller 排除，实现包内不含无关模块代码。
3. **可供后续下载的功能使用签名 Feature Pack**，但只针对边界清晰、可独立运行的功能，例如下载管理、动漫标签器、额外分析器。
4. **独立功能优先使用 sidecar**，避免把任意 Python 代码动态注入主后端。
5. 图片、视频、资源库、设置、搜索、回收站等共享核心保持编译进主包，不做任意热插拔。

模块启用状态是本地配置；关闭模块不删除用户数据。动态模块必须带：

- `module_id`、版本、依赖、最低核心版本
- 前端入口、后端入口或 sidecar
- 数据库迁移
- 文件 SHA-256 和发布者签名
- 安装、停用、卸载和版本兼容信息

## 考虑过的方案

| 方案 | 为何不选 |
|------|----------|
| 只做功能开关 | 包内仍有全部代码，不满足目标 |
| 所有模块拆成微前端/微服务 | 当前共享契约太多，维护和测试成本过高 |
| 全部模块动态加载 | Electron 外部 JS 和 Python 动态插件安全和兼容风险大 |
| 只做多个固定 Edition | 实现简单，但后续加模块需要换安装包，不能完全满足按需下载 |
| Edition + 签名 Feature Pack/sidecar | 分阶段兼顾包体积、可维护性和后续扩展，作为当前建议 |

## 后果

正向：

- 无模块代码进入安装包，包体积和认知负担下降。
- 后续可通过签名模块增加独立功能。
- 核心资源库不会被插件化拆散，降低回归风险。
- 模块边界清晰后，菜单、搜索、导入、监听目录更容易按范围裁剪。

代价/限制：

- 需要一次模块边界重构，不能只靠 UI 隐藏。
- Edition 会带来多个构建组合和发布测试。
- 动态模块需要签名、兼容矩阵、迁移和卸载策略。
- 需要维护模块 API，不能随意改核心契约。
- 核心资源类型仍然不能完全按需下载。

需要同步的地方：

- 菜单、路由守卫、类型标签、首页、搜索、导入、监听目录。
- 后端导入、扫描、统计和迁移。
- 发布流程、模块安装器和自动更新。
- 安全策略：只允许可信签名模块，限制外部代码权限。
