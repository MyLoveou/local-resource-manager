# 经验总结

## 何时写

| 场景 | 类型前缀 | 例子 |
|------|----------|------|
| 踩了一个坑并解决 | `踩坑` | `12-踩坑-TS7与vue-tsc不兼容` |
| 引入/用透一个技术点 | `技术` | `36-技术-CLIP在本仓的两种用法` |
| 做了一个设计取舍 | `设计` | `35-设计-AI建议为什么要做成闭集` |
| 讲清一个概念（纯学习向） | `学习向` | `40-学习向-AI名词到底是什么意思` |
| 用图讲清结构与流程 | `图解` | `45-图解-进程线程与并发` |

**判定顺序**：先问「读者最想知道什么」——是「怎么避坑」→ 踩坑；「这东西怎么用」→ 技术；「为什么这样设计」→ 设计；「这是什么」→ 学习向；「它怎么跑起来的」→ 图解。

## 放在哪（跨项目共用）

```text
temp/经验总结/<项目>/<两位序号>-<类型>-<主题>.md
```

- 为什么集中：同一个坑会在多个项目重复出现，各写各的等于互相看不见；
- 项目名用仓库目录名；序号在项目目录内连续；
- 索引：`temp/经验总结/README.md`，按**主题**分组、每行标项目，便于跨项目查。

### 项目怎么拿到 temp

- 业务仓把 temp 作为 submodule（或本地链接）挂进来；
- 拿不到时：先写项目本地 `docs/经验总结/` 并标 `待迁移`，下次有 temp 时移过去。

## 先搜后写

写之前先搜 `temp/经验总结/`（按现象、按机制、按标签）：

- 已有同类 → 补充或链接，**不新建重复**；
- 确认是新问题 → 新建，并在索引对应主题下挂一行。
## 一条笔记的骨架

```markdown
# <序号> · <主题>

> 一句话结论：这次解决了什么，用了什么思路。

## 为什么

（背景：不做会怎样；做了有什么代价）

## 原理

（机制层面讲清楚：数据怎么流、谁在什么时候做了什么）

## 怎么验证

（读者能自己跑的最小实验 / 对照；给出预期结果）

## 边界

（什么情况下不成立；什么时候该用别的做法）

## 延伸

（一条进一步学习方向：概念 / 文档 / 源码入口）
```

篇幅：**一屏到两屏**（100–200 行）。讲不完就拆成两篇，不要写成 500 行的书。

## 「学习指导」怎么写

这是这类笔记与普通技术文档最大的区别。三步：

1. **先给现象**：读者能观察到的表象（报错、卡顿、结果不对）；
2. **再给机制**：为什么会这样（一层就够，别一次讲到寄存器）；
3. **最后给实验**：一个 5 分钟内能自己动手、并且能推翻/确认这个机制的实验。

实验要具体到能复制：

```text
改 X 这一行 → 重跑 Y 命令 → 观察 Z 从 A 变成 B
```

「去读源码」「多练习」不算学习指导。

## 索引维护

`temp/经验总结/README.md` 维护一张表（按主题分组，跨项目）：

| # | 项目 | 标题 | 类型 | 一句话 |
|---|------|------|------|--------|
| 12 | gitmove-v2 | TS7 与 vue-tsc 不兼容 | 踩坑 | 版本不匹配导致类型检查全挂 |

新增笔记时同步加一行；序号接着最大值 +1。

## 质量清单

- [ ] 第一段能让没参与的人看懂「解决了什么」
- [ ] 有「为什么」而不只是「怎么做」
- [ ] 有一个可复制的验证实验
- [ ] 有边界说明（什么时候不适用）
- [ ] 有且只有一条延伸方向
- [ ] 没有逐行解释代码
- [ ] 索引已同步

## 反例

| 不要 | 为什么 |
|------|--------|
| 「本次重构提升了可维护性」 | 空话，不可验证 |
| 贴 200 行 diff 说「改动如上」 | 读者自己能看 diff |
| 「深入学习 React 原理」 | 不是可执行的学习指导 |
| 把 AI 的思考过程复述一遍 | 读者要结论与机制，不要流水账 |
