# 定方向

先写下一句能指导取舍的话，再让构图、字体、色彩和素材朝它靠拢。克制是留下最有力量的选择、删掉没有贡献的元素。好不好看、任务走不走得通，分开验收。

这是**新界面或用户明确要求重做视觉**时的方法。已有产品的密度、色和字默认沿用，不要换皮成另一款产品。

## 和本库其他技能怎么分

| 意图 | 用谁 |
|------|------|
| 先停下来等确认，并走 OpenSpec / 设计文档 | `project-spec-design`。方法用本技能，确认前不改业务代码 |
| 点名了改哪、只动观感 | `project-spec-style`，不要开方向 |
| 已有表面按设计证据找问题，只出计划 | `improve-ui` |
| 间距、字、圆角、阴影、无障碍、动效性能 | `better-layout`、`better-typography`、`better-ui`、`baseline-ui`、`fixing-accessibility`、`fixing-motion-performance` |
| 模型、交互、模块拆分 | `project-spec` 设计阶段 |
| 并排看已有组件变体，或自由摆放试验 | `component-canvas`、`create-canvas` |

默认只推荐**一个**方向。用户明确要求比较时，才做多个，规则见 [references/design-direction.md](references/design-direction.md)。比较时版式、字体、配色、主视觉四项里，任意两个方向最多一项相同。

本库门禁优先于源技能里的「确认一次就一路做到底」：方向卡写完就停，等用户说按这个做。用户说「你定」或「直接做」时，仍只做一个方向，并写明理由；新页面或新流程在写业务代码前还要过 `project-spec`。

## 主线

没过门槛不往后走。

1. **产品事实**。用户、品牌、任务、真实内容、设备、已有素材、技术限制。产品参考和交互参考分开写。缺的标未知，不用别的产品的内容填自己的事实。
2. **主角 / 主动作**。每屏一个主角、一个主动作。同权重的次要动作先合并或降级。对象名称、判断依据、当前状态和主动作不能当装饰删掉。
3. **概念**。从一个具体东西出发：材质和它所在的环境、一个有时间地点的场景、一个性格，或另一个领域里最有辨识度的一两个手法。不从「简约」「高级」出发。至少一个候选从本产品特有的对象或动作长出来。
4. **灰度结构**。先画主视口的灰阶线框，排清层级、对象、主动作和状态。结构走不通就退回，不用颜色和字体遮。说服型页面的骨架见 [references/direction-persuasion.md](references/direction-persuasion.md)。内容页和工作区的首屏就是内容本身，不放解释这页是干什么的口号。
5. **方向卡**。字段和差异检验见 [references/design-direction.md](references/design-direction.md)。发给用户后这一轮结束。
6. **实现**。只在用户确认之后。先做代表性的一页或核心流程和关键状态，再铺开。示例内容像真的，画面上不写「示例」「未接入」。不伪造业务成功、评价或指标。
7. **真实画面**。在目标视口打开看，桌面和另一端代表宽度都要看。没看画面不算视觉验收。设备范围见 [references/layout-and-viewport.md](references/layout-and-viewport.md)。看不了画面就写「未验证实际视觉」，不打分。

过程笔记放在该能力的文档目录或用户指定的地方。不要把过程文件、对比稿路径写进正式界面。

## 什么时候不走完整主线

| 范围 | 做法 |
|------|------|
| 用户点名了元素和改法：改文案、调一个间距、换一个已有颜色 | 直接改。改了颜色或间距时，看一眼改动处和相邻元素 |
| 只说不好看，没说改哪里 | 不算小改动。先判断是沿用现有语言修，还是用户要重做方向 |
| 存量里优化、改流程、加功能 | 沿用现有视觉。改流程和加功能不重新探索风格。从共享变量和组件改，不另造一套 |
| 几份设计文档互相打架 | 列出冲突交给用户。不擅自合并或删除 |
| 按截图还原 | 以参考图为基线，不重新发散。纵向留白按真实界面舒展，不把压缩过的稿子逐像素描下来。见 [references/layout-and-viewport.md](references/layout-and-viewport.md) |
| 只要评审、不要改文件 | 新稿按 [references/visual-review.md](references/visual-review.md)。已有产品按 `improve-ui`。交完报告就停 |

模糊词必须翻译成看得见的决定。「高级」要说清字体对比、分隔方式和色相数量；翻译不出的词从理由里删掉。对照表在设计方向参考里。

## 实现时守住的几条

- 既有项目复用有效的变量和组件。不为一次调整另造设计系统。
- 动效默认不加。用户明确要求，或说服型页面要把某一处做成记忆点时，才做那一两处，并服从 `better-ui` 与 `fixing-motion-performance`。不要为了凑「三处动效」或滚动叙事去加动画。
- 记忆点只留一两处，其余安静。优先放在用户真会做的动作、完成任务的那一下、空状态。跟产品无关的复古道具不要套。
- 颜色第一来源是品牌、实物和内容。黑白加一种强调色也是完整的色彩身份。一个视图一个强调色，见 `baseline-ui`。
- 只跑项目自己的类型检查和 lint。构建失败、接口报错这类和画面无关的环境问题记一笔，不借设计去改配置。
- 100% 和 200% 缩放下看关键区域。文字重叠或靠很小的字才装下，回到内容和布局修。

## 交付说明

方向确认之前，只交方向卡：感觉、首屏、核心动作、字体、色彩、主视觉，加上推荐理由。

实现之后写明：选定的方向和理由；改了什么、没做什么；做了哪些动效（没有就写没有）；看过哪些视口；独立评审派了没有。没有隔离的、能看图的评审者时，自己按评审参考自查，并写「未独立评审」。

看不了图、没有可运行环境时，不说视觉或交互已经通过。
