# 按证据改进界面

审计一块连贯的产品表面，对照真正管着它的那套设计。保住产品识别度，复用已有所有者。没有证据就不要出发现。只给用户选中的改动写计划，由别的流程去实现。

## 边界

- 不改产品源码。只允许在 `design-plans/` 下新建或修改计划。
- 不装依赖、不跑格式化、不提交、不推送，也不以其他方式改工作区。
- 不更新设计文档。若文档该改，写进计划，交给执行方。
- 渲染证据只用用户提供的，或用户明确要求看画面时才用。
- 每份计划自洽。执行方没有这次审计和对话的上下文。

## 1. 选定表面

尊重用户给的范围。请求很宽时，选一个可部署应用、一族代表主任务的表面，并写明选了什么。不要把整个仓库合成一个产品。

从该表面的路由和布局出发，沿渲染路径追组合、共享组件、变体、解析后的 token 和样式。不要先全库搜索不一致。

连接必须能证明：渲染、import、props、已解析的配置、CSS 继承，或该表面加载的生成物。同名、token 相似、目录靠近、概念相关，都不算连接。其他应用、预览、配置器、生成的注册表、遗留系统和另一套企业变体，除非出现在这条路径上，否则排除。

## 2. 重建局部系统

查看 `DESIGN.md`、`设计.md`、仓库指引和表面附近的设计文档。只有证明它现行且管着这块表面，才能当依据。草稿、提案、迁移和任务单是未来意图，除非已被接受且现行。没有设计文档本身不是一条发现。

只看这条路径上的 token、变量、主题、原语、变体和组合。别名和变体解析到定义。只有仓库自己这么说时，才把实现标成本地或遗留。

记录：

```markdown
## 设计语言
- 审计表面：
- 设计来源：
- 已记载的决定：
- 管辖的所有者与调用方：
- 明确例外：
```

`明确例外` 写「未记载」，除非引用的来源明确指出例外。

## 3. 证明发现

先看这条路径上的用户可见文案、激活态、响应式分支和兄弟变体，有没有自相矛盾。结果只是候选。

发现的修正必须主要改变视觉呈现、界面文案、布局、组件样式，或对已记载设计规则的符合度。若修正主要是让功能能用，就丢掉。

搜索结果、重复、实现差异只产生候选。留下候选必须同时有三条证明：

1. **契约**：引用对这个属性和范围有约束力的设计决定，或同一任务里用户可见呈现或内容的直接矛盾。「最好」「通常」、名字、省略、重复、没有写例外，都不构成契约。
2. **运行时**：证明被引用的所有者、值或行为，经追踪到的运行路径到达受影响表面。不要比较不同所有权层或不同生命周期。
3. **修正**：证据要求的那一处改动。若依赖已有 token、变体、原语或范例，写出精确名字。证据定不了正确选择、条件含糊、方案里有并列选项，或修正需要发明产品意图，就丢掉。

源码能证明 token、字体、颜色、间距、布局、文案、组件变体、响应式呈现，以及明确设计契约被违反。它不能把功能行为、状态管理或交互对错变成设计发现。层级、主次、密度、清晰度、可发现性、易用性和观感一致，需要渲染或用户证据。

用户没明确要求时，丢掉无障碍和 HTML/ARIA 发现（那是 `fixing-accessibility`）。也丢掉坏路由、重定向、数据接线、操作失败、元数据、包 API、性能、架构和代码质量，除非用户要求，或产品自己的设计契约管着它们。

三条证明都过了才写置信度。证据支持时复用已有所有者。不要因为重复就新建共享原语。

## 4. 复核

报告前重新打开每一处引用，试着推翻候选。出现下面任一情况就删掉：

- 问题与引用的实现并不一致
- 规则不管这个属性和这块表面
- 反证说明差异是有意的
- 证据支持多种修正
- 修正发明了产品意图
- 另一条发现说的是同一个根问题

只有留下的才能进表。

## 5. 报告

按置信度、用户影响、波及面、修正成本排序。最多三条。

```markdown
## 设计语言
- 审计表面：
- 设计来源：
- 已记载的决定：
- 管辖的所有者与调用方：
- 明确例外：

## 发现
| # | 问题 | 证据 | 建议改动 | 范围 | 置信度 |
| --- | --- | --- | --- | --- | --- |

## 先改这一条
<杠杆最高的一条及原因，或没有有依据的建议。>
```

证据要同时说明契约、运行时关系和确定的界面后果。建议改动只有一处修正。缺列（含置信度）的行删掉。`先改这一条` 只选一条，不要合并。

没有候选留下时：发现写「没有有依据的发现。」先改这一条写「没有有依据的建议。」

有发现就停，问用户要把哪条写成计划。用户已经选了，或明确要求为描述过的改进写计划，就按那个范围继续。用户说直接改时，仍只给计划，不实现。

## 6. 写下选中的改动

读 [references/plan-template.md](references/plan-template.md)。每个选中的改动一份计划，不要按症状拆。

写之前重新打开引用，能拿到就记下当前 commit，标出可复用的原语和范例，并追受影响表面。已有计划就修订，不要再写一份。

仓库已有 token 或组件契约时，不要发明数值。只有证明现有系统表达不了、并且写明哪些调用方该共用时，才引入新原语。

若要求核对旧计划：按当前源码和已记载决定重查，更新过时证据、受影响表面和状态。
