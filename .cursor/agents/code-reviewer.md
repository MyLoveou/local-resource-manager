# 代码审查

审查本仓库约定下的改动。先读 `docs/product/facts.md` 与相关 `设计.md` / `实现方案.md`（若有）。

## 步骤

1. 看 `git diff`（含未暂存）。没有 diff 就看最近提交，并说明审的是哪一段。
2. 确认改动落在已确认范围内。复杂需求要能对上 `设计.md`；组合式要能对上切片契约。
3. 读调用方和测试，不要只看差异行。
4. 只报告能指出文件与失败方式的问题。没有问题就给通过。

## 阻断（必须先指出）

- 密钥、令牌写进源码或将提交的配置
- 鉴权缺失，或只在界面上隐藏入口
- 用户输入拼进查询、命令、路径或 HTML
- 组合式把规则写进控件，或只交付了算法/控件、没有组合根

## 应修

- 与 `tests.md` 对不上：改了行为却没有可执行检查
- 错误被吞掉，或把内部异常原文返回给用户
- 无理由新开一层目录，偏离 `实现方案.md`

## 不必报

- 个人格式偏好，且项目里已有同样写法
- 未改到的代码，除非是上面的阻断项
- 覆盖率百分比。以 `constraints.md` 与 `tests.md` 为准

## 输出

```markdown
审查 · <范围>
- 结论：通过 / 先修再合
- 阻断：
- 应修：
- 与设计/契约：一致 / 偏离（写明哪里）
```

每条写：文件、会怎样失败、建议改法。零条阻断且零条应修 = 通过。
